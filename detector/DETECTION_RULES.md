# Detection rules

## 1. 总体原则

工具检测 GitHub PR 范围内可直接观察到的编码 Agent 痕迹。任意一条明确规则命中，该 PR 即记为 `agent_trace_detected`；否则为 `no_trace_detected`。数据本身未完成采集时输出 `unavailable`。

检测只使用已登记的启发式规则；未命中规则的内容直接忽略，不做额外语义判断。

## 2. R1：作者身份

同时检查：

- PR 作者；
- 每个 commit 作者。

使用 login、email 和完整 name 与已登记 Agent 身份进行匹配。login 会兼容 GitHub 常见的 `[bot]` 后缀，但已知 Agent 始终优先于普通 Bot 分类。

## 3. R2：Co-Authored-By

解析 commit message 中标准的：

```text
Co-Authored-By: Name <email>
```

若 name/email 对应已知 Agent，则记录 Agent 证据。

## 4. R3：文本归因短语

在 PR body 和 commit message 中匹配已登记的 Agent 归因短语，例如：

```text
Generated with Codex
Generated by Claude Code
Implemented using Qwen Code
Written by Kimi Code
```

匹配以基础短语为单位，不要求整行属于固定句式。因此，只要已登记的归因短语与 Agent 名称在文本中出现即可记录证据，例如：

```text
This PR was generated with Kimi Code
Most changes were generated with Claude Code
🤖 Generated with Claude Code
```

自由文本规则只接受能够明确指向编码 Agent 或 Agent 模式的名称。结构化作者身份可以保留较宽的身份规则，但这些宽泛名称不会自动扩展到 PR body / commit message。比如：

```text
Generated with Claude           # 不命中
Generated with Claude Code      # 命中 Claude Code
Generated with Copilot          # 不命中
Generated with Copilot Coding Agent  # 命中 Copilot
Generated with Gemini           # 不命中
Generated with Gemini CLI       # 命中 Gemini
Generated with Cursor           # 不命中
Generated with Cursor Agent     # 命中 Cursor
Generated with Qwen Coder       # 不命中
Generated with Qwen Code        # 命中 Qwen Code
```

普通提及同样不会命中，例如：

```text
Support Kimi Code models
```

R3 不解析文档结构或句子语义，只进行基础短语匹配。为兼容常见 Markdown 展示形式，程序会在临时匹配副本中处理简单的行内 Markdown 包装和链接文本；原始证据文本不会被修改，正文中的下划线、波浪号、邮箱、URL、列表符号或装饰字符不会被全局删除。

## 5. R4：Agent 任务链接

对规则目录中明确登记的任务 URL 进行匹配。R4 直接从原始 PR body / commit message 中搜索 URL，因此普通裸链接和 Markdown 链接目标都可以检测，同时保留原始任务 ID。当前会检查协议、主机名、路径和任务标识，避免相似域名直接误判。

## 6. R5：PR 元数据

检查：

- PR head branch；
- PR 当前 labels。

只使用当前可见的 branch/label，不追溯历史 label event。

## 7. 行为者归属

作者身份和文本证据会根据数字 actor id 区分：

- `target_author`：目标 PR 作者；
- `other_author`：PR 中其他 commit 作者；
- `unknown`：无法可靠确定行为者。

branch/label 证据单独记录为 metadata，不自动归因给目标作者。

因此，`agent_trace_detected=true` 只表示 PR 范围内存在 Agent 痕迹；需要判断 PR 作者本人是否使用 Agent 时，应进一步查看 `target_author_agent_trace`。

## 8. Bot 处理

处理顺序：

1. 先匹配已知编码 Agent 身份；
2. 未命中 Agent 时，再匹配已知普通自动化账号；
3. 其他 `*[bot]` login 标为未知 Bot；
4. Bot 分类不会停止 message/body/branch/label 的继续检测。

这避免了把带 `[bot]` 的真实编码 Agent 直接排除。

## 9. 规则表

`config/rules/agents.json` 为编码 Agent 规则表，可维护：

- `aliases`：仅用于 R3 自由文本和无结构化身份的显式 Co-Authored-By 名称；应优先使用明确的 Agent 产品/模式名，避免裸模型名或宽泛品牌名；
- `identity.logins`
- `identity.emails`
- `identity.names`
- `branches`
- `labels`
- `task_links`
- `source_refs`

`config/rules/automation_identities.json` 仅用于区分普通自动化账号，不直接产生 Agent 阳性。

不同 Agent 能留下的公开痕迹并不完全相同，因此规则表中的具体启发式组合也不要求完全一致：有的 Agent 同时具有作者身份、branch/label 或任务链接规则，有的当前主要依赖明确文本归因。检测器不据此给 Agent 分级、打置信度分数或划分类别；所有已登记规则都按同一套启发式命中原则处理。


## 10. 范围边界

规则目录只登记作为编码 Agent 或明确 Agent 模式参与软件开发任务的工具。泛化 AI 标记以及为 Agent 提供配置同步、规格工作流或任务管理的辅助工具不作为 Agent 本体产生阳性。
